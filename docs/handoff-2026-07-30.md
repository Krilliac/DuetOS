## DRSH TCP wire path bug — investigation status

**Symptom:** DRSH accepts TCP connections (SYN-ACK works), but fails to
send ServerHello back — client gets "Connection reset by peer."

**Confirmed working:** child TCB created with correct routing; snd_wnd=65535,
cwnd=5840, mss_send=1460 on init; SocketAccept wraps child in Socket with
connected=true.

**Prime suspect:** `tcp_segment.cpp:~1044` — `t.snd_wnd = u32(win) << ws`
runs BEFORE the SynRcvd→Established transition. If QEMU SLIRP's completing
ACK has a zero or tiny window field and snd_wscale amplifies it wrong (or
zeroes it), EffectiveSendWindow returns 0 and DrainSendBuffer silently
breaks without sending anything. The connection then times out and resets.

**Debug next steps:**
1. Pop stash, add `KLOG_DEBUG_V("net/tcp", "drain-entry", snd_wnd)` at
   DrainSendBuffer entry and at the line-1044 snd_wnd update
2. Rebuild with `-DDUETOS_DRSH_AUTOSTART=ON`, boot QEMU
3. Connect with `tools/security/drsh_attack.py`, read serial log
4. If snd_wnd==0 confirmed: fix by clamping child TCB's snd_wnd to at
   least 1 MSS during SynRcvd→Established, or by not applying wscale
   to the handshake-completing ACK (RFC 7323 says scaling applies only
   after the handshake, but the code applies it to all non-SYN segments)

**Secondary suspect:** SocketSendStream reads Socket fields without pool
lock (lines 748-772); race between accept-thread populating connected/tcb
and DRSH thread's first send. Low probability.
